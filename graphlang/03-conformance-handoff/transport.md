# Candidate P0 transport profile T0

Proposed only; no adoption, parser implementation or runtime conformance is claimed. This addendum resolves the raw-input gaps in [P0](../02-minimal-semantics/contract.md), pinned at Oasis `4fc03a76c8f4faa7014173deba86c348b08c3ab0`. It does not change that historical contract. Any implementation must explicitly select both P0 and T0; P0 alone leaves these questions open.

## Ordered rules

- **T1 Bytes:** accept at most 1,048,576 bytes inclusive. Reject larger payloads as invalid_request before decoding. Require strict UTF-8 without BOM. Invalid encoding or BOM is invalid_request. This is an invocation payload bound, not an HTTP request/header limit.
- **T2 Syntax:** require exactly one JSON value, with only JSON whitespace before/after it. Reject malformed/trailing JSON, duplicate decoded keys at any object depth, non-JSON NaN/Infinity and unpaired Unicode surrogates as invalid_request. Escaped surrogate pairs decode to one scalar. Duplicate detection follows JSON escape decoding, without Unicode normalization. These are transport errors before graph validation; this explicitly refines P0 R1's otherwise ambiguous duplicate-key error classification.
- **T3 Parser bounds:** reject container depth above 16, counting the top-level object/array as depth 1, and numeric tokens longer than 128 ASCII characters as invalid_request. Enforce before recursive allocation/numeric conversion; token length counts sign, decimal point and exponent. These are new candidate limits, not existing P0 facts. At/below the limits, normal syntax and semantic checks still apply. Implementations must not expose native parser exceptions as results.
- **T4 Envelope:** after T1–T3, require an object with a graph key; otherwise invalid_request. Then apply P0 graph validation before other request-field validation. A present but invalid graph is invalid_graph. Missing/unknown remaining fields use invalid_request after graph validation. This resolves missing-envelope precedence while retaining P0 precedence for ordinary graph/request collisions.
- **T5 Numbers:** parse JSON numbers exactly as decimal mathematical values, without intermediate binary-float rounding. For integer-valued request fields, accept any legal JSON numeric spelling whose exact value is an integer in that field's range: 2, 2.0 and 2e0 denote the same input. Normalize negative zero to integer 0. Reject fractions/out-of-range values according to their field (invalid_request for input/path/budget). A numeric graph cell remains invalid_graph, even if its value is 1. Boolean/string values are never numbers. Preserve exactness before range checking, including values just outside the carrier. Do not materialize enormous powers of ten; use the bounded token's significand/exponent to determine range and integrality.
- **T6 Result:** after successful transport/normalization, apply P0 evaluation unchanged. All transport failures return `{ok:false,code:"invalid_request",steps:0,at:null}`. Graph validation failures use invalid_graph with steps 0/at null. Emit success numbers and counters as ordinary decimal integer tokens; P0's carrier stays unchanged. No partial output or mutation on failure.

For multiple T1–T3 defects the public result is the same; no parser-specific message/offset is normative. Depth limits apply even inside unknown fields. Duplicate or Unicode defects inside graph are transport failures, while a validly decoded graph with bad shape is invalid_graph. Escaped brackets inside strings do not contribute container depth.

## Evidence and handoff

[transport-fixtures.json](transport-fixtures.json) contains exact byte payload recipes, byte counts, SHA-256 digests, rule mappings and authored expected results. A recipe is hex bytes followed by a declared number of ASCII spaces; this keeps size-limit fixtures small. The materializer never silently repairs input. The suite uses complete invocations for numeric tests, not isolated number tokens. Exact-size and one-byte-over cases use a valid identity invocation plus trailing whitespace.

Run `python3 graphlang/03-conformance-handoff/verify_transport.py` to check package integrity and materialized-byte counts/hashes. This does not parse requests or execute Graph Lang. A future authorized transport adapter must receive the exact materialized bytes, not a parse/reserialize of them. Record raw captures, exact source revision and command; compare using `verify_transport.py --responses capture.json`. Capture format is the README format, with the transport contract/suite hashes printed by this checker. A matching capture remains unattested until the producer/logs are reviewed.

T0 chooses exact numeric value semantics to match P0's integer carrier without tying validity to JSON number spelling. Tradeoffs for founder review: extra parser work versus integer-token-only input; uniform transport errors versus nested graph-specific duplicate errors; explicit depth/token bounds versus implementation-defined parser limits. Recommendation: adopt T0 only as part of the disposable P0 experiment. Source implementation still requires separate authorization. CTO should retain unavailable as an adapter error outside this profile.

The fixture suite is a bounded acceptance set, not an exhaustive parser test suite. Remaining work is independent review of the proposed rules, adoption, then implementation and real byte-to-result evidence. Further fixture growth alone does not establish runtime readiness.
